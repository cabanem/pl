## Layer 1 — Literal scan with step-level locus

Walk each recipe's step tree rather than flat-grepping the file, so hits arrive as `(recipe, step_number, field)` — the locus improvement you identified last time. Three places the literal can hide in a recipe export:

```python
import json
from pathlib import Path

NEEDLE = "_mapping"
hits = []

def walk(block, recipe, path=""):
    for i, step in enumerate(block or []):
        loc = f"{path}/{i}:{step.get('name','?')}"
        # 1. input mappings (datapill formulas, static strings)
        for k, v in (step.get("input") or {}).items():
            if NEEDLE in json.dumps(v):
                hits.append((recipe, loc, f"input.{k}"))
        # 2. schemas (a JSON-parse step consuming _mapping names it here)
        for sk in ("extended_input_schema", "extended_output_schema"):
            if NEEDLE in json.dumps(step.get(sk) or []):
                hits.append((recipe, loc, sk))
        # 3. embedded Python source rides in input['code'] — covered by (1),
        #    but flag it separately since it needs human reading, not just detection
        walk(step.get("block"), recipe, loc)

for p in Path("recipes").glob("*.json"):
    r = json.loads(p.read_text())
    code = r["code"] if isinstance(r["code"], dict) else json.loads(r["code"])
    walk([code], p.stem)
```

Cheap corroborating check while that runs: grep your regenerated **OpenAPI spec v2** for `_mapping`. It was derived from this same corpus's schemas — absence there is weak evidence (specs describe interfaces, not internals), but a *hit* there would short-circuit everything.

## Layer 2 — Enumerate raw-JSON consumers (the sufficiency half)

This is where the IR earns its keep. You're answering: *which steps receive the content of a config or variant JSON file?* Two-stage query against the IR:

**2a. Find the download sites.** Filter the IR's step inventory for Drive download actions whose file-ID input datapill traces back to `drive_id_config_json`, `config_json_file_id`, or `template_file_ids` (the wire names from `Payload.provision`/`validate`/`preview`). Your existing edge extraction already resolves datapill provenance across `call_recipe` boundaries via the `input.flow_id`/`zip_name` bindings, so follow the same chains: R-1 → PRV-01 → down the provisioning pipeline, plus the validate and preview entry points. In practice this should land on a small set — likely PRV-family and TPL-family steps.

**2b. Classify each consumer as named-key or wildcard.** For every step downstream of a download, ask what it does with the content:

- **Passes it to `parse_config_file`** → clean, choke point applies, `_mapping` dies there.
- **Workato JSON-parse step** → its schema is the extraction contract; Layer 1 already checked schemas, so no `_mapping` in schema = not extracted.
- **Python step** → pull the `code` input and read it. You're looking for two patterns: the literal (Layer 1 caught it) and **wildcard consumption** — `for k in cfg`, `cfg.items()`, `cfg.keys()`, `len(cfg)`, or re-serializing the whole dict (`json.dumps(cfg)`) onward. Given your parse-once-at-the-boundary discipline, I'd bet the Python steps destructure named keys — but this is the one place the verdict requires eyes on code, not pattern matching.

If 2b comes back all-named-keys with no `_mapping` among them, you have the full proof: the literal doesn't exist anywhere (Layer 1), and no consumer *could* touch it without the literal (Layer 2).
