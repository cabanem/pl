Good news first: the drop-ins landed faithfully — `Util.toIsoDate`, the three Preflight edits, the Payload wire field and `_requireArgs`, the Provision threading and schema guard, the version triplet with the 7.0 history line, and the full migration chain including the 1.0 bridge are all in place and correct. But I found **one critical bug**, one inconsistency between a migration claim and the code, and a handful of smaller items. In severity order:

## 1. CRITICAL: `Labels.variant_count` vs `Labels.variantCount` — variants silently never generate

In `003_Schema.js` the key landed as snake_case:

```javascript
variant_count:        'How many variations are there of the template?'
```

But `Variant._readVariantCount` reads `Labels.variantCount` — camelCase, per the drop-in. `Labels.variantCount` is therefore **undefined**, and `findValueRightOfLabel`'s guard (`if (!sheet || !label) return null`) turns that into `null`, which `_readVariantCount` converts to `0` — a *legitimate* state, so no error anywhere. Net effect: **every provision and validate generates zero variant templates**, `template_file_ids` ships empty, and nothing complains. This is the D6 landmine's replacement being armed by a key-name typo — the exact silent-nil failure class, one level up (key→key instead of label→cell). Fix: rename the key to `variantCount`.

And since this class of bug now has two members (the connector kv drifts, this key mismatch), it's worth closing structurally — you already have a load-time guard block in `003_Schema.js`; add one line to it:

```javascript
  // Labels keys referenced by library code must exist - a missing key
  // reads as undefined and produces silent nulls, not errors.
  ['customerName','analystEmail','targetVMS','applicationName','folderId',
   'reminderDays1','reminderDays2','reminderDays3','supplierInstructions',
   'kickoffEmailBody','hasSeedData','seedDataDriveId','seedDataSheetName',
   'seedDataIndexKey','expectedDate','variantCount'].forEach(function(k) {
    if (!(k in Labels)) throw new Error('Schema.gs: Labels.' + k + ' is referenced by library code but not defined.');
  });
```

That converts this whole failure mode from "variants quietly vanish" to "library refuses to load with the key named."

## 2. The `_mapping` migration note claims something the code doesn't do

The 1.2→1.3 entry pushes: *"_mapping is no longer serialized to config JSON as of schema 1.3... confirmed unconsumed."* But `CONNECTOR_SHEETS` and `CONNECTOR_SHEETS_ORDER` **still contain `'_mapping'`**, and `008_Variant.js`'s passthrough list still names it. So the note writes a false claim into every migrated workbook's audit trail, and the fingerprint drift the removal was meant to fix persists. Two valid resolutions: if the corpus trace came back clean, remove `'_mapping'` from both structures (the load guard will keep you honest); if the verdict is still pending, delete the note from the migration entry — the gate comment in the drop-in was meant as "don't ship this line until confirmed," and right now the note shipped without the change.

## 3. Three-way sync on the reworded label — two copies still owed

You changed the wording from the placeholder to `'What is the target completion date?'` — fine, but that string now has two unpaid dependents: the **template/workbook cell** must read exactly that (the migration will append it correctly for migrated workbooks, but the master template needs the manual edit), and the **connector kv key** must be `kv["what is the target completion date?"]` — not the "expected completion date" wording from drop-in block 9a, which is now stale against your actual label. Small related cosmetic: the missing-fields message says `'Expected completion date'` while the label says "target" — harmless (it's display prose), but the analyst error message naming a field slightly differently from the question they're looking at is mild friction; consider `'Target completion date'`.

## 5. Shim observations (unchanged, but two things the review surfaced)

**The invitations menu wiring bypasses the library entirely.** The menu binds "Send supplier invitations" → `sendAllInvitations`, which posts a hand-rolled `{analyst_email, ssId}` payload to a hardcoded webhook URL — no `batch_id`, no `payload_version` stamp (that's `Webhook.call`'s invariant, and this doesn't go through it), no Result, no logging. Meanwhile the proper `sendInvitations` shim — which calls `SDC.Invitations.run` and renders per-supplier results — exists in the same file, orphaned from any menu item. If the hardcoded path is a temporary bridge, fine, but it's the only Workato call in the system outside the transport layer, and it sends a different wire shape than `Payload.invitations` defines.

**The validation modal filters on `c_status` only.** `validationResultsHtml_` buckets checks by `c.c_status === 'fail'/'warn'`, while `ValidationReport.toModel` deliberately reads `c.c_status || c.status` because the field name varies by envelope. If a verdict ever arrives with plain `status` (which is what the connector's `validate_config` emits natively), the modal's fail/warn arrays come up empty and it renders "✓ Validation passed" over a failing verdict. One-line hardening: `var st = c.c_status || c.status;` and bucket on that — mirroring the library's own resolution keeps the modal and `_validation_results` incapable of disagreeing, which was the stated point of `toModel`.
