The opacity is structural, so let's fix the diagnosis problem first — because `ValidationReport.write` currently has **three distinct failure paths that all collapse into the same bare `{ ok: false }`**, and two of them never log anything at all:

1. **`_extractVerdict` returns null** — the response carried no recognizable `checks[]` array at any of the four known wire locations. Returns `ok: false` with **no console.warn, no log line, nothing**. Completely silent.
2. **Sheet unavailable** — `ensureSchema` swallowed its own failure (it's try/catch-warn), then the `!sheet` check returns `ok: false`, also silently.
3. **A real exception during the write** — this one *does* `console.warn(e.message)`, but `console.warn` goes to the **Executions panel** (Extensions → Apps Script → Executions, click the run), *not* to `_script_logs`. The orchestrator then writes only the generic "ValidationReport.write did not complete" to the sheet. So the reason exists — in a different log than the one you're reading — or doesn't exist at all.

Two pieces of evidence you can check right now, no code changes: the **Executions entry for the failing run** — if there's a `ValidationReport.write failed: ...` warning there, that's path 3 and the message names the cause. And if this is the *validate* flow, the SUCCESS line in `_script_logs` already contains the first 200 characters of the parsed response (`'Validation complete. Returned: ...'`) — read it and see whether a `checks` array is visible and *where it's nested*. If checks live somewhere `_extractVerdict`'s four candidates don't cover (a new envelope, e.g. `parsed.result.validate_summary`), that's path 1.

**My ranked bet depends on which flow this is.** If it's **provision**: path 1, and arguably not a bug at all — `Provision.run` unconditionally calls `ValidationReport.write(response.parsed, ...)`, but the provision endpoint's response only carries a verdict when the recipe includes one; a response without `checks[]` extracts to null and manufactures a scary warning out of a normal state. If it's **validate**: path 1 via envelope drift is still the favorite (the comment in `_extractVerdict` itself says the verdict "has been seen at several wire locations" — you've been bitten by shape movement here before, which is probably the familiar part), with path 3 as runner-up.

The durable fix is to make the function say why. Drop-in for `000_ValidationReport.js`:

```javascript
ValidationReport.write = function(ss, parsed, correlationId) {
  try {
    if (!ss) return { ok: false, rowsWritten: 0, reason: 'no-spreadsheet', detail: '' };

    var verdict = ValidationReport._extractVerdict(parsed);
    if (!verdict) {
      // Name the shape we actually received, so envelope drift is
      // diagnosable from _script_logs instead of invisible.
      var keys = (parsed && typeof parsed === 'object')
        ? Object.keys(parsed).join(', ') : String(parsed);
      return { ok: false, rowsWritten: 0, reason: 'no-verdict',
               detail: 'No checks[] at any known location. Top-level keys: [' + keys + ']' };
    }

    ValidationReport.ensureSchema(ss);
    var sheet = ss.getSheetByName(VR_SHEET_NAME);
    if (!sheet) {
      return { ok: false, rowsWritten: 0, reason: 'sheet-unavailable',
               detail: 'ensureSchema could not create/find ' + VR_SHEET_NAME +
                       ' (see Executions panel for its warning).' };
    }

    var rows = ValidationReport._toRows(verdict, correlationId);

    if (VR_CLEAR_BEFORE_WRITE) {
      var lastRow = sheet.getLastRow();
      if (lastRow > 1) {
        sheet.getRange(2, 1, lastRow - 1, VR_HEADERS.length).clearContent();
      }
    }
    if (rows.length > 0) {
      var startRow = VR_CLEAR_BEFORE_WRITE ? 2 : sheet.getLastRow() + 1;
      sheet.getRange(startRow, 1, rows.length, VR_HEADERS.length).setValues(rows);
    }
    return { ok: true, rowsWritten: rows.length, reason: null, detail: '' };
  } catch (e) {
    return { ok: false, rowsWritten: 0, reason: 'exception', detail: e.message };
  }
};
```

Then thread the reason into the sheet log at both call sites — in `Validate.run` and `Provision.run`, the `else` branch of the report check becomes:

```javascript
    } else {
      reportWarnings.push('Could not write results to _validation_results (' +
        report.reason + '): ' + report.detail);
      log('WARNING', 'ValidationReport.write did not complete (' +
        report.reason + '): ' + report.detail);
    }
```

(In Provision it's the `warnings.push` near the end rather than `reportWarnings` — same edit.) And one behavioral refinement for Provision specifically: since a provision response legitimately may carry no verdict, treat `reason === 'no-verdict'` there as an INFO ("endpoint returned no validation verdict; nothing to write") rather than a WARNING — otherwise every verdict-less provision cries wolf, which is exactly how warnings stop being read.
