That log is the smoking gun, and it's a genuinely interesting one. Look at the contradiction in Section 3: the diagnostic (running in the **container**) says `raw` is `[Date]` — its `instanceof Date` check passes — yet `toIsoDate` (running in the **library**) returns null, which can only happen if *its* `instanceof Date` check fails on the same object. Both are telling the truth.

**Root cause: `instanceof` is context-sensitive across the Apps Script library boundary.** The container script and the SDC library each have their own global scope, which means each has its own `Date` constructor. Your `ss` object is created in the container (`SpreadsheetApp.getActiveSpreadsheet()` in main.js) and passed into the library, so every `Date` that `getValues()` mints off that spreadsheet belongs to the *container's* context. When that Date reaches `Util.toIsoDate` inside the library, `value instanceof Date` checks it against the *library's* `Date` constructor — different constructor, `false`. The value falls through to the string branch, `String(containerDate)` produces `"Mon Jul 14 2026 00:00:00 GMT-0400..."`, the regex rejects it, null. MALFORMED branch fires on a perfectly good Date.

You've already documented this exact failure class on the other side of the platform — your note about `is_a?` being unreliable on response objects in the Ruby connector. This is the JavaScript twin, and the fix is the same move: **brand check instead of identity check.** `Object.prototype.toString.call(value)` returns `'[object Date]'` regardless of which context constructed it:

```javascript
// 000_Util.js — replace the first branch of toIsoDate:
Util.toIsoDate = function(value, tz) {
  // NOT `value instanceof Date`: instanceof is context-sensitive across the
  // GAS library boundary. A Date minted from a container-created Spreadsheet
  // fails `instanceof Date` inside the library (separate globals, separate
  // Date constructors). Object.prototype.toString is the cross-context-safe
  // brand check.
  if (Object.prototype.toString.call(value) === '[object Date]') {
    return Utilities.formatDate(value, tz, 'yyyy-MM-dd');
  }
  var s = String(value === null || value === undefined ? '' : value).trim();
  return /^\d{4}-\d{2}-\d{2}$/.test(s) ? s : null;
};
```

**And the same latent bug exists in `Drive.normalizeDates`** — `if (cell instanceof Date)` — which means it has been silently *not normalizing* container-context Dates all along. It never surfaced because, until now, no connector sheet carried a true Date cell (your fingerprint investigation found numeric serials and text timestamps, never a live Date on this path). But your new field is a true Date on `1_customer`, which *is* serialized: unfixed, it skips normalization, hits `JSON.stringify`, and lands in the config JSON as `"2026-07-14T04:00:00.000Z"` — a UTC datetime instead of `"2026-07-14"`, carrying exactly the timezone-shift hazard §6.7 exists to prevent, and arriving at the connector's kv parse in the wrong shape. Same one-line fix:

