# ADR — OBS-01 enforces phase and error_type asymmetrically

## Context

OBS-01's Python step validates two closed vocabularies on the way into EventLog: `phase` (28 values, defined in `taxonomy_event_phase.md`) and `error_type` (11 values, defined in `taxonomy_error_type_event-log.md`). It also has a documented but unimplemented third layer — the `phase × error_type` matrix (Section 5 of the error_type doc) — that constrains which combinations are valid.

We have to decide how strictly each layer enforces. The strict choice is symmetric: every violation forces the event into an "incident" shape (severity → error, value → sentinel) so downstream queries notice. The lenient choice is symmetric the other way: annotate-and-pass-through for everything, trust callers to do the right thing.

Neither symmetric choice fits. The two vocabularies have different roles, different blast radii on misuse, and different empirical risk profiles.

## Decision

**Three-tier asymmetric enforcement:**

1. **`phase` — heavy-handed enforcement.** A bad phase value forces `severity=error`, replaces `phase` with the sentinel `invalid_phase`, and preserves the original values in `details_json`. The event still writes; it just writes loudly.

2. **`error_type` — light-handed enforcement.** A bad error_type value is dropped to empty string with the original preserved in `details_json._original_error_type`. `severity` and `phase` are unchanged.

3. **`phase × error_type` matrix — not enforced.** Section 5 of the error_type taxonomy doc remains advisory. Callers are expected to honor it; OBS-01 doesn't check.

## Rationale

**Phase is the primary classifier.** Every reasonable EventLog query starts with `WHERE phase = ...`. A typo here corrupts the column silently: an event that should have been `validation_failed` lands under `validatin_failed`, the dashboard count is off, and nobody knows. Forcing the event into incident shape ensures someone notices fast.

**Error_type is a secondary classifier.** Queries filter by phase first, error_type second. A typo'd error_type makes the event harder to slice but doesn't lie about what happened. A `validation_failed` event with `error_type=""` instead of `error_type=submission_content_invalid` is still a real validation failure — it just shows up as "uncategorized" in error-type breakdowns. The annotated drop is proportional.

**Matrix mismatches are usually caller confusion, not data corruption.** A `validation_passed` event with a stray `error_type` value, or a `validation_failed` event with no `error_type`, doesn't make the event wrong — it makes the event under-categorized in the same way the light-hand drop does. Enforcing the matrix at the Python layer trades caller flexibility for marginal forensic gain. The discipline lives in the caller's recipe code (the v2 doc maps verdict_status → error_type explicitly for VAL-01, for example) and is verifiable by reading those recipes.

**Asymmetry is honest.** The strict-everything path looks principled but conflates three different problems and over-fires. The lenient-everything path under-fires on the one that matters. The asymmetric path matches enforcement intensity to query criticality, which is what the operator actually wants.

## Consequences

- Operators searching EventLog for problems must check `details_json._validation_error` to surface light-hand drops and matrix mismatches. A future "data quality" dashboard could surface these proactively.
- The "Pending" decision in the error_type taxonomy doc ("strict or warn for matrix?") is resolved as "neither at the Python layer; advisory in the doc." Future tightening is not blocked — promoting the matrix to enforced is a Python edit, not a data migration.
- If a value-level typo on `error_type` happens often enough to fragment queries despite the annotation, the decision can be re-litigated to heavy-handed on `error_type` too. The annotated drops are findable evidence for that conversation.
- `invalid_phase` is added to the phase taxonomy as a reserved sentinel, only emitted by OBS-01 self-validation. Recipes do not emit `invalid_phase` directly.
