## ADR-001: Collapse Apps Script to Thin Webhook Trigger

**Status:** Accepted

**Layer:** System boundary / integration

**Description:** Reduce Google Apps Script from a full provisioning control plane to a minimal menu-driven webhook trigger. The entire backend (`ProvisioningRunner`, `InventoryService`, `WorkatoClient`, `FleetManager`, `RegistryService`, `ManifestService`, `AppContext`) is eliminated. What remains is `onOpen()` → menu item → read Sheet → validate → fire `UrlFetchApp.fetch()` → toast.

**Context:** The original GAS backend was a web app (`doPost`) that authenticated inbound calls, checked out workspaces from a fleet registry in Google Sheets, provisioned Workato data tables and environment properties via the Workato Developer API, tracked state in `_runtime_state`, generated business IDs, and fired a bootstrap webhook. This worked, but it distributed authority across two systems — GAS co-authored entity identities, managed fleet state, and maintained its own manifest cache. The 401 authentication errors we debugged (traced to regional endpoint routing and incorrect API paths) were a symptom of this split: GAS was making direct API calls to Workato infrastructure it didn't own.

**Decision:** Apps Script's only job is to originate requests. An analyst clicks a menu item, GAS reads four fields from the Sheet (`client_name`, `analyst_email`, `target_vms`, `config_file_id`), stamps `correlation_id` (UUID) and `timestamp`, validates that required fields are non-empty, and fires one webhook to Workato. The Sheet becomes stateless — it holds analyst inputs and nothing else.

**Rationale:**
- GAS's unique advantage is living inside Google Workspace (native Sheet/Drive access, user-context auth, menu items). Everything else it was doing, Workato can do natively without an API hop.
- Eliminating `doPost` removes the web app deployment, auth token checking, `WEBHOOK_SECRET`, and the entire request/response wrapper.
- The 401 class of bugs becomes structurally impossible — GAS never calls the Workato API.
- The codebase collapses from ~5 dense files to effectively two: config and menu handler.

**Alternatives considered:**
- **Keep GAS as thin pass-through with `doPost`:** Still requires web app deployment and auth. The trigger is a Sheets menu action, not an inbound webhook, so `doPost` serves no purpose.
- **Eliminate GAS entirely, have Workato poll Sheets or use a Google Forms trigger:** Loses the native Sheets UX (menu items, toasts, input validation before submission). The analyst experience matters — they live in Sheets.

**Consequences:**
- `001_Workato_Client.gs`, `002_Provisioning.gs`, `003_Fleet.gs`, `005_Repair.gs` are deleted permanently.
- `_runtime_state` on the Sheet is no longer written or read. No `template_project_id`, `template_version_id`, or `supplier_request_map_json` persisted in the Sheet.
- All diagnostic and repair tooling moves to Workato recipes.

## ADR-002: Workato Home Base Project as Control Plane

**Status:** Accepted

**Layer:** Orchestration / topology

**Description:** Designate a single Workato project ("base project") as the control plane for all provisioning, routing, registry, versioning, and cross-client operations. This project contains the webhook endpoint, three home base Data Tables (`WorkspaceRegistry`, `Requests`, `Manifests`), five orchestration recipes (`R-00`, `R-1`, `R-1b`, `R-2a`, `R-2b`), the manifest file in FileStorage, the template recipe bundle, and the SDC Platform Connector.

**Context:** Authority over the platform was split — GAS owned fleet assignment, idempotency checking, manifest hashing, and bootstrap orchestration, while Workato owned per-client runtime (data tables, validation, supplier interaction). This created a co-authoring problem: GAS pre-generated `template_project_id`, `template_version_id`, and `supplier_request_id[]`, sent them to Workato, then persisted the response mappings back to the Sheet. Two systems disagreed about who owned entity identity.

**Decision:** Workato owns both the orchestration layer and the runtime layer. The base project is the single point of entry (webhook), the single source of truth for fleet state (WorkspaceRegistry), request lifecycle (Requests), and template versioning (Manifests). It holds zero client data — after provisioning, each client folder runs independently.

**Rationale:**
- Workato can query its own Data Tables natively without an API hop, making registry lookups, idempotency checks, and manifest reads trivial.
- All business IDs are generated by the recipe that creates the row (convention: UUID, never pre-generated upstream). This eliminates the identity co-authoring problem.
- Version freezing happens in one system: R-2a stamps `manifest_id` on Requests at provision time; there's no opportunity for GAS and Workato to disagree about which version is active.
- The base project is deliberately thin — three tables, five recipes, two assets. Its job ends after provisioning.

**Alternatives considered:**
- **Hybrid control plane (GAS + Workato):** The status quo. Rejected because it required maintaining state in two places and the handoff was the source of most bugs.
- **External orchestrator (Cloud Function, Lambda):** Adds infrastructure outside both systems. Workato already has callable recipes, Data Tables, and webhook triggers — an external orchestrator doesn't add capability, only complexity.

**Consequences:**
- Three new Data Tables in the base project: `WorkspaceRegistry`, `Requests`, `Manifests`.
- The Google Sheets fleet registry is retired. No more `FleetManager.checkoutWorkspace()` with `LockService`.
- Recipe-to-recipe handoffs within Workato replace GAS-to-Workato webhook chains.

## ADR-003: Single Workspace with Multi-Workspace Seam

**Status:** Accepted

**Layer:** Topology / future-proofing

**Description:** Build for Case A (all client folders in one Workato workspace) while designing the abstraction that makes Case B (multi-workspace) a routing-only change.

**Context:** The platform needs per-client isolation (each client gets its own folder with its own tables, recipes, and Workflow App). Today, one workspace is sufficient. In the future, workspace splits may be needed for capacity, regional data residency, or client security requirements. The original GAS backend had fleet management (`FleetManager`, `RegistryService`) that was tightly coupled to the provisioning flow — splitting workspaces would have required rewriting multiple systems.

**Decision:** `WorkspaceRegistry` exists in the base project with one row today. The webhook payload includes `workspace_id` as a reserved field (null/ignored for now). `R-1b` (Route Request) is a near-passthrough today but is the designated insertion point for routing logic. When multi-workspace is needed, `R-1b` reads `workspace_id` from the request or from a routing rule, and dispatches to the appropriate workspace's bootstrap recipe via its API. The per-project bootstrap logic (R-2a) and everything downstream stays identical.

**Rationale:**
- The cost of the abstraction today is near-zero: one Data Table row, one passthrough recipe, one reserved payload field.
- The future migration is additive — add a routing decision to R-1b, register new workspaces in `WorkspaceRegistry`. No changes to Apps Script, no changes to per-client recipes.
- `WorkspaceRegistry.api_endpoint` and `api_token_ref` (a property name, never the actual token) are the only fields needed to address a remote workspace.

**Alternatives considered:**
- **Build multi-workspace now:** Premature. One workspace handles current load. The abstraction boundaries are in place; the implementation can wait.
- **No abstraction, retrofit later:** Cheaper today, expensive later. R-1b as a routing seam costs almost nothing.

**Consequences:**
- `R-1b` exists even though it's currently a passthrough. This is intentional.
- `WorkspaceRegistry` has fields (`api_endpoint`, `max_capacity`) that are unused in Phase 1.

## ADR-004: `correlation_id` as Universal Tracing Key

**Status:** Accepted

**Layer:** Cross-cutting / observability

**Description:** A single UUID, generated by Apps Script at webhook time, threads through every recipe handoff, every Data Table entity, and every Workato API call header (`x-correlation-id`) for the lifetime of a data collection request.

**Context:** The original system had multiple IDs serving overlapping purposes: `workspace_binding_id` (fleet tracking), `bootstrap_id` (provision tracking), `template_project_id` (business entity), and various generated UUIDs written to `_runtime_state`. Tracing a failure required correlating timestamps across GAS logs, Workato job history, and Sheet state — none of which shared a common key.

**Decision:** Apps Script generates one UUID (`Utilities.getUuid()`), sends it as `correlation_id` in the webhook payload. R-1 writes it to `Requests`. Every downstream recipe passes it on handoff. It's stamped on `WFA_TemplateProject.correlation_id` and `WFA_SupplierRequest.correlation_id` in the per-client project. Workato's platform logs tie API call failures to it via the `x-correlation-id` header. GAS logs it at send time.

**Rationale:**
- One key spans the full chain: GAS log → Workato webhook trigger → recipe job history → Data Table records.
- Idempotency becomes a simple check: R-1 queries `Requests` for existing `correlation_id` before creating a duplicate row. Double-clicks and retries are handled.
- `workspace_binding_id` is absorbed — the correlation_id serves the same function now that Workato owns both assignment and provisioning.

**Alternatives considered:**
- **Separate `client_id` and `correlation_id`:** Adds a concept without adding value. Collapsed to one ID.
- **Stamp `correlation_id` on every entity (including `RUN_Upload`, `RUN_FieldError`):** Considered and deferred. The hop from `RUN_Upload.supplier_request_id` → `WFA_SupplierRequest.correlation_id` is short enough. Denormalization can happen later if cross-client reporting demands it.

**Consequences:**
- Every recipe's input schema includes `correlation_id`.
- Every callable recipe handoff passes it explicitly.
- The webhook contract is the origin — no server-side generation of the tracing key.

## ADR-005: Five-Point Version Chain of Custody

**Status:** Accepted

**Layer:** Data integrity / versioning

**Description:** Template version identity is frozen at five discrete points in the recipe chain. Each freeze copies the version reference from the upstream entity — it's inherited, never looked up from a "current" flag.

**Context:** The original system had a mutable `current_version_id` field on `WFA_SupplierRequest` that stored internal Workato record IDs instead of business UUIDs (RISK-01 from the data model analysis). This meant a version change could silently affect in-flight supplier requests. There was no documented chain showing which recipe froze which field or when.

**Decision:** The chain is:

1. **R-2a** stamps `manifest_id` on `Requests` → ties the entire client project to a specific manifest version.
2. **R-2b** creates `VER_TemplateVersion` with `status = published` → all CFG_* rows are hydrated against this version; it's immutable after publish.
3. **R-008** stamps `assigned_version_id` on each `WFA_SupplierRequest` → ties each supplier to the published version.
4. **R-007a** copies `template_version_id` from `WFA_SupplierRequest.assigned_version_id` onto `RUN_Upload` → inherited, not looked up.
5. **R-002** copies `template_version_id` from `RUN_Upload` onto `RUN_ValidationResult` → direct traceability, immutable.

All status fields are forward-only. No rollbacks.

**Rationale:**
- Copy-forward means no recipe ever reads a "current" pointer that could change between write and read. Version drift is structurally impossible.
- Each freeze point is owned by exactly one recipe, making debugging unambiguous: if `RUN_ValidationResult` has the wrong version, R-002 is the only place to look.
- The chain is auditable: given any `RUN_ValidationResult`, you can walk backward through the chain to the original manifest.

**Alternatives considered:**
- **Single version stamp at provisioning time, all downstream reads from one location:** Simpler but fragile. A lookup-based approach means any concurrent version change (publish v2 while v1 suppliers are active) silently corrupts in-flight data.
- **Version column on every table:** Overkill. The chain already provides traceability; denormalizing to CFG_* rows would add write cost without adding query value.

**Consequences:**
- Once R-008 has frozen `assigned_version_id` on any `WFA_SupplierRequest`, the CFG_* rows scoped to that version must not change. Immutability is a convention enforced by recipe logic, not by Workato platform constraints.

## ADR-006: Split R-2a and R-2b (Infrastructure vs. Business Data)

**Status:** Accepted

**Layer:** Recipe architecture

**Description:** Provisioning is split into two callable recipes: R-2a (Provision Client Folder) handles infrastructure — 13 tables, deferred relations, recipe cloning, rebinding, Workflow App setup, and bookkeeping. R-2b (Parse & Hydrate Config) handles business data — pulls the config spreadsheet from Drive, parses each sheet, hydrates CFG_* tables and `VER_TemplateVersion`, and publishes the version.

**Context:** R-2a was already the heaviest recipe in the system (13 table creates, 3 deferred relations, 5 recipe clones, Workflow App setup). Adding sheet-by-sheet config parsing (7 sheets, each with different schemas and cross-references) would create a 25+ step monolith that's nearly impossible to debug when step 19 fails.

**Decision:** R-2a creates the infrastructure; R-2b populates it with business data. R-2a calls R-2b at its final step, passing `request_id`, `correlation_id`, `project_folder_id`, `table_results_map`, `config_file_id`, and `template_file_ids`. Both live in the base project (not the client folder) because they run once during provisioning and need Drive access.

**Rationale:**
- If config parsing fails, R-2a already succeeded — the client folder exists with valid but empty tables. R-2b can be re-run without reprovisioning infrastructure.
- Each recipe has a clear responsibility: R-2a is IaC, R-2b is data hydration. Debugging is scoped.
- R-2b replaces what was previously an entirely manual and undocumented configuration phase (C-1 through C-7). Making it a separate recipe makes the automation explicit and testable in isolation.

**Alternatives considered:**
- **Monolithic R-2a:** Rejected for debuggability and partial-failure recovery reasons.
- **R-2b in the client folder:** Rejected because it needs Drive access for the config file and runs once during provisioning — it's an orchestration concern, not a runtime concern.

**Consequences:**
- The full provisioning chain is now: R-1 → R-1b → R-2a → R-2b → R-008. Five recipe hops from webhook to operational client folder.
- `table_results_map` (the bridge between R-2a's table creation and R-2b's data hydration) must be serialized and passed between recipes.

## ADR-007: Config File as Source of Truth, Parsed Once

**Status:** Accepted (refined in v2.1.0)

**Layer:** Data flow / integration

**Description:** The master config spreadsheet (Google Sheets) is the single source of truth for field definitions, validation rules, lookups, variants, suppliers, and users. Apps Script generates XLSX templates from it. The webhook carries a pointer (`config_file_id`) to the config file; Workato pulls and parses it once during provisioning (R-2b), writes the parsed JSON to FileStorage, and stores the `parsed_config_file_id` on `WFA_TemplateProject`. Downstream recipes (R-008) read from FileStorage, not from Drive.

**Context:** In the v2.0.0 design, both R-2b and R-008 pulled from Google Drive — R-2b to hydrate CFG_* tables, R-008 to parse supplier/user sheets. This meant two Drive round-trips, two parse passes, and a runtime dependency on Drive availability for the client-folder recipe.

**Decision (v2.1.0 refinement):** R-2b parses the config once, writes the full parsed JSON to FileStorage, and stores the FileStorage ID on `WFA_TemplateProject.parsed_config_file_id`. R-008's input changes from `config_file_id` to `parsed_config_file_id`. R-008 reads from FileStorage — no Drive dependency.

**Rationale:**
- Parse once, read many. The config file is frozen at provisioning time; re-parsing it is wasted work.
- Client-folder recipes should not depend on external systems (Google Drive) that the base project's orchestration layer already accessed. The FileStorage artifact is internal to Workato and always available.
- The parsed JSON artifact is auditable — it captures exactly what configuration was active at provision time, independent of subsequent Sheet edits.

**Alternatives considered:**
- **Embed config in the webhook payload:** The config can be large (hundreds of lookup values, dozens of fields). The webhook stays lean; heavy data is pulled, not pushed.
- **Both R-2b and R-008 pull from Drive (v2.0.0):** Works but creates an unnecessary external dependency for R-008 and duplicates parse logic.
- **Store parsed config in a Data Table column:** Data Tables have cell size limits. FileStorage handles arbitrary JSON size cleanly.

**Consequences:**
- `WFA_TemplateProject` gains `parsed_config_file_id` (schema v3.1.0).
- R-008 has no Google Drive dependency.
- The parsed config JSON in FileStorage is an auditable artifact tied to the `correlation_id`.

## ADR-008: Multi-User Supplier Model (`WFA_SupplierUser`)

**Status:** Accepted

**Layer:** Domain model / per-client schema

**Description:** Portal access is decoupled from supplier request identity. `WFA_SupplierRequest` represents a supplier-level engagement (one per supplier per data collection cycle). `WFA_SupplierUser` represents an individual person who can access the portal and upload files on behalf of that supplier.

**Context:** The original model used `WFA_SupplierRequest.contact_email` as both the outreach target and the portal access key. This assumed one person per supplier. Real-world usage shows multiple people at a single supplier (e.g., a primary contact and a delegate) need portal access and upload capability.

**Decision:** `contact_email` stays on `WFA_SupplierRequest` as the primary contact for outreach emails (R-004). Portal access is scoped by `WFA_SupplierUser.user_email`. The Workflow App scoping filter changes from `contact_email = current_user` to a join: `WFA_SupplierUser.user_email = current_user → supplier_request_id → WFA_SupplierRequest`. R-008 creates both `WFA_SupplierRequest` and `WFA_SupplierUser` rows, with the first user's email copied to `contact_email`.

**Rationale:**
- Separates two concerns that were conflated: "who do we email about this request?" vs. "who can log in and upload files?"
- The config already supports this (sheet `3_users` has multiple rows per supplier). The data model now matches the config structure.
- R-007a's logic doesn't fundamentally change — the Workflow App still scopes to the right supplier request; it just resolves through one extra hop.

**Alternatives considered:**
- **Comma-separated emails on `contact_email`:** Fragile, breaks email sends, makes Workflow App scoping a string-parsing problem.
- **Defer until multi-user is actually needed:** The config sheet already has the data. Building the table now avoids a schema migration when a client first has multiple users per supplier.

**Consequences:**
- Per-client table count goes from 10 to 13 (including `WFA_SupplierUser`, `CFG_Variant`, `CFG_VariantField`).
- `WFA_SupplierUser → WFA_SupplierRequest` is a deferred relation (resolved in R-2a Pass 2).
- Workflow App configuration requires a join-based scoping filter.

## ADR-009: Manifest-Based IaC Versioning (R-00)

**Status:** Accepted

**Layer:** Versioning / deployment

**Description:** Recipe R-00 (Package & Version) snapshots the current template project definition — recipe bundle and table schemas — into a versioned manifest stored in the `Manifests` Data Table. Each snapshot produces a `manifest_id`, `manifest_hash` (SHA-256 of the canonical snapshot), and `schema_version`. Only one manifest row has `is_current = true` at any time. R-2a reads the current manifest at provision time and stamps its `manifest_id` on the `Requests` row.

**Context:** The original system had no deployment versioning. There was no tracking of which recipe bundle or schema version was deployed to a given workspace. Drift detection was schema-only (via `InventoryService._updateTableSchemaIfChanged`), not behavior-aware. The GAS `ManifestService` built a SHA-256 hash for idempotency, but it hashed the *request payload*, not the *template definition*.

**Decision:** R-00 runs on schedule or manual trigger. It snapshots the template project (table schemas from the data table manifest, recipe definitions), computes a canonical hash, and writes a `Manifests` row. The `is_current` flag is flipped atomically (old row false, new row true). Provisioning always reads the current manifest, so every client folder is traceable to exactly one manifest version.

**Rationale:**
- Every client folder is bound to a specific manifest at provision time. No ambiguity about what schema or recipe version a client was provisioned with.
- The hash enables idempotency: identical template definitions produce the same hash, so R-00 can skip a write if nothing changed.
- The snapshot in FileStorage is an auditable artifact — you can reconstruct what any client was provisioned with by reading their `manifest_id`.

**Alternatives considered:**
- **Use Workato's native project export/manifest:** Workato doesn't expose a versioned manifest API that covers table schemas + recipe definitions in a single snapshot. The custom approach is more complete.
- **No versioning, always provision from live template:** Makes it impossible to know what version a client is running when the template changes.

**Consequences:**
- R-00 must run (and succeed) before any provisioning. If `Manifests` has no `is_current = true` row, R-2a fails with a clear precondition error.
- Schema changes to the template require an R-00 run before they affect new clients.

## ADR-010: Webhook Contract Design (Lean Payload, Pointers Not Data)

**Status:** Accepted

**Layer:** Integration / API design

**Description:** The webhook payload from Apps Script to R-1 carries six fields: `correlation_id`, `client_name`, `analyst_email`, `target_vms`, `config_file_id`, `template_file_ids`, and `timestamp`. Heavy data (field definitions, rules, lookups, suppliers, users) lives in the config spreadsheet and is pulled by Workato, not pushed through the webhook.

**Context:** The original backend sent provisioning payloads that included all supplier data, generated business IDs, and metadata. The payload was the contract between two systems, and it grew as the system grew.

**Decision:** The webhook is a "please provision this client" request with pointers, not data. `config_file_id` is the Google Drive file ID of the master config spreadsheet. `template_file_ids` is an optional array of `{variant_name, file_id}` pairs for pre-generated XLSX templates. Everything else is derived by Workato from the config file.

**Rationale:**
- Lean payloads are debuggable. Six fields fit in a log line.
- The config file is the source of truth. Duplicating its contents in the webhook creates a synchronization problem (what if the Sheet changed between payload construction and webhook delivery?).
- Workato reads the config at parse time (R-2b), creating a point-in-time snapshot. The webhook doesn't need to carry that snapshot.

**Alternatives considered:**
- **Full payload with all config data embedded:** The original approach. Rejected because it made the webhook contract brittle and the payload large.
- **No `template_file_ids`, let Workato find them in Drive:** Possible but adds a Drive search step that GAS already resolved. The pointer is cheap to include.

**Consequences:**
- Apps Script must ensure `config_file_id` is a valid, accessible Drive file ID before sending.
- R-2b must handle Drive access failures gracefully (the config file could be deleted or permissions changed between webhook send and parse).

## ADR-011: SDC Platform Connector (Custom Connector for Domain Logic)

**Status:** Accepted

**Layer:** Recipe architecture / reusability

**Description:** A custom Workato connector ("SDC Platform Connector") encapsulates domain-specific operations: parse config, validate config, validate upload, and generate report. Referenced in the base project's assets.

**Context:** Complex operations like config parsing (7 sheets, cross-referencing fields/lookups/rules), upload validation (applying field rules, lookup checks, cross-field validations), and report generation (translating field errors into human-readable output) don't map cleanly to Workato's built-in actions. Embedding this logic directly in recipe steps would create unmaintainable recipes with dozens of inline scripts.

**Decision:** Domain logic that is complex, reusable, and version-sensitive lives in a custom connector. Recipes call connector actions like any other Workato action. The connector is versioned alongside the platform.

**Rationale:**
- Custom connectors are testable in isolation, versioned, and reusable across recipes.
- Recipe builders work with clean action interfaces (input schema, output schema) rather than inline Ruby/Python scripts.
- The connector boundary separates "what to do" (recipe orchestration) from "how to do it" (parsing, validation, report generation).

**Alternatives considered:**
- **Inline scripts in recipes:** Works for simple logic but becomes unmaintainable for multi-sheet config parsing or multi-rule validation.
- **External microservice (Cloud Function):** Adds infrastructure outside Workato. The connector runs inside Workato's execution environment with native access to Data Tables and FileStorage.

**Consequences:**
- Connector updates require testing against the current manifest schema.
- The connector's action interfaces become part of the platform's API contract.

## ADR-012: Automated Configuration Phase (Replacing C-1 through C-7)

**Status:** Accepted

**Layer:** Workflow / automation

**Description:** The previously manual and undocumented configuration phase (seven steps from "create template version" through "publish version") is now fully automated by R-2b. The analyst's workflow ends at "click the menu button" (step A-10). Everything from there is automated: R-1 → R-1b → R-2a → R-2b → R-008.

**Context:** Between provisioning (R-2a creates the folder and tables) and bootstrap (R-008 creates supplier requests), there was an entire manual workflow where someone had to create a template version, define fields, define rules, populate lookups, configure variants, set up error translations, and publish the version. This was undocumented in v1 and error-prone — any missed step left the client folder in a partially configured state.

**Decision:** R-2b automates all seven configuration steps by pulling the master config spreadsheet from Drive and parsing each sheet into the corresponding CFG_* tables:

| Manual step | Automated by |
|---|---|
| C-1: Create template version | R-2b step 3 |
| C-2: Define fields | R-2b steps 4–6 (parses `4_fields`) |
| C-3: Define variants | R-2b steps 11–14 (parses `6_variants`) |
| C-4: Define rules | R-2b steps 9–10 (parses `4_complex_validations`) |
| C-5: Define lookups | R-2b steps 7–8 (parses `5_lookups`) |
| C-6: Error translations | R-2b steps 15–16 (parses `_error_translation`) |
| C-7: Publish version | R-2b step 17 |

**Rationale:**
- Eliminates the most error-prone phase of the workflow. The analyst defines everything in a familiar environment (Google Sheets) and the system handles the rest.
- The analyst workflow (A-1 through A-11) is now fully documented in the system manifest's `configuration_phase` section.
- Automated hydration is deterministic and auditable — the parsed config JSON in FileStorage captures exactly what was applied.

**Alternatives considered:**
- **Keep manual configuration with better documentation:** Documentation doesn't prevent human error. Automation does.
- **Build a Workato Workflow App for analyst configuration:** Possible but premature. Analysts are already comfortable in Sheets. The Sheets→webhook→automation pipeline is working.

**Consequences:**
- Config validation before publish becomes important: R-2b should verify that every `CFG_Field` with a `lookup_name` has corresponding `CFG_Lookup` rows, every `CFG_Rule` references valid field IDs, etc. This is an open design question (noted in the manifest).
- Re-triggering the webhook after config edits raises a versioning question: create a new `VER_TemplateVersion` (v2) or reject the request? The forward-only status convention suggests a new version is correct — suppliers already bootstrapped on v1 stay on v1.

## ADR-013: Client Folder Self-Containment

**Status:** Accepted

**Layer:** Topology / isolation

**Description:** Each client folder (`SDC_{client_name}_{correlation_id_short}`) is fully self-contained after provisioning. It holds 13 Data Tables, 5 recipes, and a Workflow App — everything needed to operate a complete supplier data collection cycle without reaching back to the base project.

**Context:** The base project owns orchestration; the client folder owns operations. The boundary between them is provisioning — once R-2a/R-2b/R-008 complete, the client folder is independent.

**Decision:** After provisioning:
- Client-folder recipes (R-008, R-004, R-007a, R-002, R-006) read only from their own tables.
- The Workflow App binds to three client-local tables (`WFA_SupplierRequest`, `WFA_SupplierUser`, `RUN_Upload`).
- No client-folder recipe calls back to the base project or reads from home base tables.
- The base project updates `Requests.status = ACTIVE` and `provisioned_at` as its final act; after that, it's uninvolved.

**Rationale:**
- Isolation simplifies reasoning: anything about a specific client is inside one folder.
- Failure isolation: if one client folder's recipe errors, no other client is affected.
- Future workspace migration: a self-contained folder can theoretically be moved to another workspace without changing internal recipe logic.

**Alternatives considered:**
- **Shared lookup tables across clients:** Saves some duplication (e.g., common error translations) but creates cross-client coupling. Rejected for isolation.
- **Client recipes query base project for config updates:** Breaks the version-freezing model. Config is frozen at provisioning time.

**Consequences:**
- Any cross-client operation (reporting, monitoring, alerting) lives in the base project, not in client folders.
- Schema updates to the template require re-provisioning (or a dedicated migration recipe) — they don't propagate automatically to existing client folders.
